- **Partial data loss guard for array field sync, over rows the controls fully showed** — The array-sync guard (added in the composition editor safety sprint, issue #73) is now settled at two grains: `wouldLoseArrayData()` refuses a field when the read says nothing about any row, and `reconcileArrayItems()` settles the rest row by row, keeping any row whose read carried nothing its stored item could have produced (a non-object item, or an object holding keys the schema does not declare and so never rendered a control for). What remains unguarded is partial loss over rows whose keys WERE all on screen — 3 of 4 such rows reading back empty due to a future sync bug is byte-identical to a user clearing three rows, and guarding it would block real editing. - **Accordion serialization drift is unreachable for valid compositions** — After #223 the only shape that trips the editor's serialization-invariant gate is a composition item with no `props` key (`serializeAccordionData()` re-emits `props: {}`). That requires a component with zero required props; `nav` and `footer` were the only two, and they are now template-owned chrome and not composable. So a drifting composition is necessarily *invalid*, and `doSaveDraft()` (`assets/js/pp-admin-editor.js`) refuses it with "Fix errors first." Test 9 in `tests/e2e/composition-editor.spec.ts` was rewritten to assert exactly that, and `SchemaValidationTest::testEveryComposableComponentDeclaresARequiredProp()` pins the premise as a component-library invariant — add an optional-only component and it fails in `composer test`. Two open questions if that ever changes: whether the invariant gate still earns its keep for valid compositions (it remains defence-in-depth for corrupt/raw-written rows, which Test 8 covers), and whether the save-unlock path should be restored. No action needed today. Surfaced by /plan-eng-review on the #223 branch, 2026-07-09.
